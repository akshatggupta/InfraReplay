The loop

every stage now runs on real traffic
01

Capture

A reverse proxy records the request and response; SQLAlchemy listeners inside the app record the queries it runs.

02

Correlate

One correlation id travels from proxy to app, so every query knows which request caused it.

03

Store

Metadata in Postgres, payload snapshots in blob storage, secrets masked before either.

04

Replay

The recorded requests are re-sent at a live service — one at a time, or concurrently to reproduce a race.

05

Compare

Matched event pairs are diffed after fresh ids and clocks are normalised away.

What changed

v1 was the demo · v2–v7 made it real
Already built

v1 — the pipeline, on synthetic data

Every layer the product needs was real; only the data source was fake.

  • Event schema with versioning and a migration registry.
  • Plugin registry loading entry points, validating each against its ABC — no core code imports a plugin.
  • Mock capture generating a believable checkout, clean and buggy.
  • Replay + comparison engines, filesystem storage, default redaction.
  • API, CLI and dashboard — one source of truth, two thin clients.
This push

v2 – v7 — the same pipeline, on real traffic

Nothing above the capture layer was rewritten. That was the bet v1 made.

  • v2HTTP capture. A Starlette reverse proxy with body limits; real headers redacted on the way in.
  • v3SQL capture + correlation. In-app SQLAlchemy listeners; the app streams its queries back before the response leaves.
  • v4Live replay. Requests really sent, real answers recorded, dynamic values substituted, races reproducible.
  • v5Comparison hardening. Generated ids, UUIDs, timestamps and per-hop headers normalised before the diff.
  • v6Demo shop + a real bug. A checkout that oversells under concurrency, and a one-line fix to switch it off.
  • v7Export / import. A recording leaves as one file and replays on another instance.

Does it actually work

recorded from a live run, not written by hand

One unit in stock, two shoppers checking out at the same moment. The shop confirms both orders — it oversells. The recording is then replayed against the buggy shop, and against the fixed one.

infractl · capture → replay → compare
$ infractl capture start --listen :8082 --upstream :3000
rec_3856638fb164  listening :8082 -> http://127.0.0.1:3000

# two checkouts, fired together, through the proxy
$ curl localhost:3000/api/v1/orders
{"confirmed_orders": 2, "stock_left": 1}      <- one unit sold twice

$ infractl capture stop rec_3856638fb164
rec_3856638fb164  [completed]  32 events

$ infractl replay rec_3856638fb164 --target http://127.0.0.1:3000 --concurrency 2
summary: {'MATCH': 16, 'DIFFERENT': 0, 'MISSING': 0, 'NEW': 0, 'ERROR': 0}
# replayed against the buggy shop: the bug reproduces exactly

# fix the reservation, replay the same recording again
$ DEMO_SHOP_LOCK_INVENTORY=1 uvicorn examples.demo_shop.app:app --port 3000
$ infractl replay rec_3856638fb164 --target http://127.0.0.1:3000 --concurrency 2
summary: {'MATCH': 12, 'DIFFERENT': 2, 'MISSING': 2, 'NEW': 0, 'ERROR': 0}

DIFFERENT  postgres.result  rows_affected 1 -> 0
DIFFERENT  http.response    status 201 -> 409  body: {'error': 'out_of_stock'}   <- the fix, named

The comparison does not just say "something changed". It says the reserving UPDATE now matches no row, and the second shopper is turned away instead of being sold stock that does not exist.

Running the demo

four terminals, five minutes

Start the three services — or docker compose up --build for all of them at once.

uvicorn infrareplay.api.app:app --port 8000 uvicorn examples.demo_shop.app:app --port 3000 python -m infrareplay.dashboard.app

Seed the synthetic recordings, so there is something to show before any traffic exists.

infractl demo seed

Record real traffic: start the proxy, send a checkout through it, stop.

infractl capture start --listen :8081 --upstream :3000 curl -X POST localhost:8081/api/v1/checkout -H 'x-demo-user: dana' -H 'authorization: Bearer secret' -d '{...}' infractl capture stop <recording-id>

Open the dashboard at localhost:8080: the request waterfall, each query expandable, the masked Authorization header.

Replay it at the live shop, then at a production-looking host to show the refusal.

infractl replay <id> --target http://127.0.0.1:3000 infractl replay <id> --target https://api.production.example.com

Run the oversell story from docs/v6.md — capture the race, reproduce it, fix it, replay again.

What it does not do yet

stated, not hidden

BEGIN and COMMIT are not captured. They are issued on the connection rather than through a cursor, so the SQLAlchemy listener never sees them. Every statement inside the transaction is captured.

Result rows are not read back. Reading a cursor would consume it, so results record rows_affected and whether the statement returned rows.

A race only reproduces under concurrency. Replayed one request at a time, the second checkout simply finds the shelf empty — --concurrency is what makes the recorded race reproducible.

No performance claims. The benchmark suite is v10; until it exists, no numbers are published — that rule comes from the spec and it still holds.

Security is v8. Recordings are redacted but not encrypted at rest, and the API has no access control yet.
