# v10 — Benchmark Suite

## Goal

Measure what capture costs, under load, with a method anyone can rerun — and
make no performance claim this suite does not back.

## What is real

`benchmark/run.sh` starts its own stack — API, demo shop and payment gateway as
real processes on free ports, with throwaway databases — and drives the same
Locust workload at three load levels (5, 20 and 50 users, 30 s each), once
straight at the shop and once through capture. It reports throughput, checkout
latency at p50/p95/p99, CPU and memory per process, events and bytes captured,
how long finalising took, and whether capture lost anything: every captured
request must keep all its events, and the API's own dropped-events counter
must stay at 0. Method, machine and package versions are written into every
report. Details: [`benchmark/README.md`](../benchmark/README.md). Latest
report: [`benchmark/results/latest/report.md`](../benchmark/results/latest/report.md).

## What the first run found

The benchmark's first full run, on the code as it stood after v9, showed that
capture was not usable under load:

| Load | Direct req/s | Captured req/s | Throughput | Checkout p50, direct → captured |
|---|---:|---:|---:|---|
| light, 5 users | 27.6 | 2.8 | −89.7% | 28 ms → 1,600 ms |
| medium, 20 users | 49.5 | 3.9 | −92.1% | 100 ms → 4,700 ms |
| heavy, 50 users | 90.5 | 4.9 | −94.6% | 290 ms → 11,000 ms |

Under heavy load it also lost data: the API's SQLite hit `database is locked`
17 times, those event writes failed, and because the capture's background
writer had no error handling, the first failure ended it and the rest of that
capture was dropped without a trace. (Saved in `results/before-pooling/`.)

Three causes, each measured before it was fixed:

1. **An HTTP client built per request.** The capture proxy and the in-app agent
   each created a new `httpx` client for every request. Timed alone, building
   one costs **183 ms median** here — it loads a TLS certificate bundle. One
   pooled connection per proxy and per agent replaced them; the proxy uses a
   bare transport so no cookie jar is shared between users. A single captured
   checkout went from 325 ms to 51 ms median.
2. **SQLite lock contention.** WAL mode and a 30 s busy timeout for the API's
   database, and event writes that retry on a lock.
3. **A writer that could die.** The capture writer now batches whatever is
   queued into one transaction, and a batch that still fails is counted
   (`infrareplay_events_dropped_total`) and logged — never silent.

The robustness fixes alone removed the failures but not the cost
(`results/robustness-only/`: no lock errors, still −89% to −94%). Pooling is what
moved the numbers (`results/pooled/`):

| Load | Throughput, before → after | Checkout p50 added, before → after | Complete requests | Dropped |
|---|---|---|---:|---:|
| light | −89.7% → **−25.0%** | +1,572 ms → **+65 ms** | 100% | 0 |
| medium | −92.1% → **−63.9%** | +4,600 ms → **+414 ms** | 100% | 0 |

The heavy level of that run is excluded: a test suite was started on the same
machine during its captured window, so the two competed for CPU. The final
report below was run with nothing else running.

| light, 5 users | 24.9 | 21.8 | -12.3% | +33 ms | 100% | 0 | 0 |
| medium, 20 users | 29.4 | 22.3 | -24.0% | +150 ms | 100% | 0 | 0 |

Full report, raw runs and method:
[`results/latest/report.md`](../benchmark/results/latest/report.md).

The shop's own direct throughput is lower than in the earlier runs because
every checkout now waits on the gateway call while holding its database
transaction — the shop's cost, identical in both modes, not capture's.

## Two traps in measuring, both fixed in the harness

- **Locust's timer fired early.** `--run-time` is scheduled on gevent's loop
  clock, which goes stale while Locust's imports block; on this slow filesystem
  a "10 s" run measured 4 s of load. The harness drives Locust as a library
  (`drive.py`) and divides by the window it timed itself.
- **Completeness by totals read over 100%.** Requests still in flight when the
  load stops are captured but never counted by Locust. Completeness is judged
  per request instead: each captured request must carry all its events.

## DoD

`benchmark/run.sh` produces a reproducible report; the README links to it; no
performance claim is made without it. Smoke-tested by
`tests/integration/test_benchmark.py`.

## Known limits

- One machine runs the load, the services and the databases; the
  direct-versus-captured comparison is like for like, the absolute numbers are
  not what dedicated hosts would show.
- Under medium and heavy load the single API process — proxy, ingest and
  writes — is the ceiling for captured throughput. Several workers, or the
  proxy in its own process, would lift it; neither is built.
- SQLite by default; `--api-db` / `--shop-db` measure another backend.
