# v3 — Real PostgreSQL Capture + Correlation

## Goal

Tie the database work an application does back to the HTTP request that
caused it, on real traffic.

## What is real

- **`postgres_capture`** (`infrareplay/plugins/postgres_capture/`) — a
  `CapturePlugin` that listens to SQLAlchemy's `before_cursor_execute` /
  `after_cursor_execute` on the application's own engine. App-level
  instrumentation, not a wire proxy, which is the scope the spec sets.
- **Correlation context** (`infrareplay/capture/context.py`) — contextvars
  holding the recording and correlation ids for the request in flight. No
  context bound means nothing is captured, so an instrumented app records
  nothing while no capture is running.
- **The agent** (`infrareplay/agent/`) — the app-side half:

      proxy ──(recording id, correlation id)──> app
                                                 │ SQL
                                       capture plugin queue
      ingest API  <──── flush(), before the response is sent ────┘

  Flushing before the response leaves the app means the proxy never records
  a response whose database events have not landed yet — no polling, no
  sleeping, no lost events.

- **Correlation on write** (`infrareplay/recording/correlate.py`) — events
  from two processes arrive out of order. On `stop`, they are grouped by
  `correlation_id`, ordered by `timestamp_ns`, re-sequenced gap-free, and
  the DB events are parented to the request that caused them.

## DoD

One really recorded HTTP request that triggers several queries shows every
event under one `correlation_id`, in causal order, in the v1 dashboard:

```
 0 http.request     POST /api/v1/checkout
 1 postgres.query   SELECT users...
 2 postgres.result
 3 postgres.query   SELECT inventory...
 ...
15 http.response    201
```

Verified by `tests/integration/test_live_capture.py` and
`tests/unit/test_correlate.py`.

## Known limits

`BEGIN` / `COMMIT` are issued on the connection, not through a cursor, so
they are not captured — the statements inside the transaction are. Result
*rows* are not read back (that would consume the cursor); `rows_affected`
and `returns_rows` are recorded instead.
